## Behaviour

**Tool results in traces**

- **B1.** The tracer receives the tool's results: the `Tracer` protocol's
  `tool` method gains the list the tool returned (empty on an error call),
  and `agent._execute` passes it. Every tracer (`NoopTracer`,
  `LangfuseTracer`, `SafeTracer`, `run.py`'s recording tracer and
  `_FanOutTracer`) takes it.
- **B2.** `LangfuseTracer.tool` sends as the tool observation's output
  `{"result_count": n, "results": [...]}`. `results` is exactly what the
  model received for that call (the same rows, the same fields: id, name,
  brand, category, price_eur, in_stock, specs, description), at most the
  first 10 rows. On an error call it is `[]`, with level `ERROR` as today.
  Nothing else is added to what Langfuse receives.
- **B3.** B1 and B2 apply to every run, `uv run advisor` and eval runs
  alike. A run's answer, exit code and stdout do not change; a failure while
  tracing results is swallowed like any other tracing failure.

**Dimensions on eval traces**

- **B4.** An eval case with §9 dimensions gets three more tags after §12's
  five: `feature:<v>`, `scenario:<v>`, `persona:<v>`, in that order, each
  only when the case has that dimension. Values are written as in the case
  file (spaces kept). A case without dimensions gets §12's five tags only.

**The queue command**

- **B5.** `uv run advisor-analysis queue <report>` (a §8/§9 run report)
  needs the three `LANGFUSE_*` variables (the environment merged with
  `.env`, as `advisor-eval` reads them). Missing ones: it prints which, and
  exits 2 without calling Langfuse.
- **B6.** It ensures a `BOOLEAN` score config named `pass` exists (reuses
  the first one with that name and data type; creates it otherwise,
  description "pass/fail label; the critique goes in the comment"). A config
  named `pass` with another data type: it exits 2 naming the conflict.
- **B7.** It ensures a queue named `advisor-eval <stamp>` exists, where
  `<stamp>` is the report's stamp (`--queue <name>` overrides the name). A
  new queue is created with the `pass` config. An existing queue is reused
  only if its score configs include `pass`; otherwise it exits 2.
- **B8.** It selects the report's cases by optional filters, combined with
  AND: `--feature`, `--scenario`, `--persona` (exact dimension value),
  `--status PASS|FAIL|ERROR` (the case's §8 status). No filter selects all
  cases.
- **B9.** It finds the run's traces: root observations whose trace tags
  include all of `eval` and `run:<stamp>`, read with the `trace_context`
  field group, and maps each `case:<id>` tag to its trace id. A selected
  case with no trace is counted as "no trace" and skipped. Two traces with
  the same case tag: the latest start time wins, and the count of such
  duplicates is printed.
- **B10.** It adds each selected case's trace as a `TRACE` item, skipping
  traces already in the queue. It never changes or deletes an item, a
  queue, a config, a score or a trace.
- **B11.** It prints one summary line: queue name, items added, already
  queued, no trace, and exits 0. Any Langfuse error prints `Langfuse <step>
  failed: <error type>: <message>` (no keys) and exits 2, after the items
  already added.

**The import command**

- **B12.** `uv run advisor-analysis import <report>` (`--queue <name>`,
  default as B7; `--labels <path>`, default `evals/labels/<report
  stem>.jsonl`) needs the variables as in B5, and exits 2 if the queue does
  not exist.
- **B13.** It reads the queue's annotation scores: `source=ANNOTATION`,
  the queue's id, name `pass`, with the `details` and `subject` field
  groups, following the cursor to the end.
- **B14.** It maps each score's trace id to a case through the run's traces
  (B9). Scores on traces outside this run are counted and skipped. Several
  scores for one trace: the one with the latest timestamp wins.
- **B15.** A score becomes a label: `true` → `pass`, `false` → `fail`;
  `critique` is the score's comment (empty if none); `labelled_at` is the
  score's timestamp; `question` and `answer` come from the report. A `fail`
  without a comment is not written; it is counted as "fail without
  critique" and its case id printed.
- **B16.** It appends one label line per case whose current label in the
  labels file differs in `label` or `critique` (or has none). Running it
  twice appends nothing the second time. Lines written by the viewer are
  never rewritten; the last line per case still wins, so an import after a
  viewer label overrides it, and the reverse.
- **B17.** It prints one summary line (labels written, unchanged, fail
  without critique, outside the run) and exits 0. Errors as in B11, with
  nothing written for a failed read.
- **B18.** `taxonomy` and `counts` read the imported labels unchanged: an
  imported file is a §9 labels file.

**Where the code lives**

- **B19.** All `langfuse` calls of B5–B17 are in `tracing.py`, behind a
  protocol (`Annotations`) defined in an SDK-free module. The selection,
  matching and label building of B8, B9, B14–B16 are pure functions over
  that protocol's plain data. `analysis.py` wires the two subcommands;
  `tracing.py` is imported only when one of them runs.

## Interpretations

- **I1.** "each tool call's results (the products returned: at least id,
  name, price and stock)" (intent): read as the same rows the model saw,
  not a subset, so a reviewer judges on what the model knew. The cap of 10
  is the tool's own limit ("limit clamped to 1..10", `CLAUDE.md`), so it
  never cuts a real result today; it guards a future tool.
- **I2.** "a boolean `pass`, with the critique in the score's `comment`, or
  what the spec settles" (intent): boolean with comment, because it maps
  one to one onto §9's `label` and `critique`. A separate TEXT score would
  need two scores per trace to stay in step.
- **I3.** "the case id and §9 dimensions as tags or metadata, which can be
  filtered in the Tracing table" (intent): tags, since §12's tags already
  filter there (§12's live check). Metadata filtering is not needed.
- **I4.** "How a trace is matched back to a §9 case" (intent, question 4):
  by the `case:<id>` and `run:<stamp>` tags §12 sets, read through the
  observations API, which the SDK calls "the only real-time read path". No
  trace id is written into the report, so §12's report format stays.
- **I5.** The Scores API v3 is not called real-time by the SDK docs; a
  score just made may take minutes to appear. The import reads what is
  there; running it again later picks up the rest (B16).

## Non-functional

- **Boundaries:** `langfuse` only in `tracing.py`; the protocol and the
  pure logic in an SDK-free module under `src/advisor/evals/`; the CLI in
  `analysis.py`. The advisor's own runs keep "tracing never changes a run".
  Only `queue` and `import` report a Langfuse error to the owner.
- **Data:** what Langfuse newly receives is the synthetic catalogue rows a
  search returned and the case's dimension values (synthetic or
  owner-written). No key, no personal data. Labels stay in
  `evals/labels/`, committed as §9 does.
- **Model use:** none. Tests make no network call (`tests/conftest.py`).
- **Autonomy:** the commands create a score config, a queue and queue
  items, and read scores and observations. They never write scores and
  never delete or update anything.
